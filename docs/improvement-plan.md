# Что улучшать дальше: разбор и порядок работ

> **Статус: план, а не обещание.** Документ отвечает на вопрос «что в проекте
> стоит улучшить и в каком порядке», но ничего из него не сделано, кроме
> отмеченного «сделано». Каждая правка отсюда — отдельная запись в
> `CHANGELOG.md` и отдельные проверки.

Разбор на 2026-10-13, от состояния `main` после PR #52 и двух открытых
изменений: PR #53 (чистка, одно правило движения, накладка генерации, этот
документ) и PR #50 (большой проход: свои шрифты, вход под замком, офлайн без
23 МБ, структура, проверки).

## Чем смотрел

Не «на глаз»: размеры и поведение измерены здесь и сейчас, остальное — чтение
кода против чек-листов из скиллов проекта (`.agents/skills/`).

| Чем | Что смотрел |
| --- | --- |
| `web-perf` | загрузка: установка офлайн-кэша, размеры сборки и сжатия, кэш-заголовки, цепочки ресурсов |
| `frontend-design` | доступность и тексты: имена у кнопок, пустые и ошибочные состояния, движение, «пол качеством» |
| `workers-best-practices` | хостинг Cloudflare: секреты, границы чтения тела, наблюдаемость, устаревший `compatibility_date` |
| `durable-objects` | хаб в Durable Object: инициализация, запись изменённого, таймеры и окно записи |
| `webapp-testing` | чем проверяем: 16 наборов в Node, семь из них в jsdom; пиксели не проверяет ничто |

Скиллы, по которым сверялся код, — свежие: `npm run skills:check` на
2026-10-13 отвечает «скиллов 20, у 0 источник ушёл вперёд», то есть чек-листы
не отстали от апстрима.

**Чего в этой песочнице измерить нельзя.** Браузера здесь нет (ни Chromium, ни
Playwright), поэтому Core Web Vitals не снимались: раздел `web-perf` про трассу
и `take_snapshot` заменить нечем. Всё, что ниже, — либо числа из сборки и
файлов, либо структура кода. Пункт «проверка в браузере» в приоритете 1
существует именно потому, что этот пробел нельзя закрыть иначе.

## Что уже в порядке (не улучшать заново)

Числа — с этой машины, на этой ревизии.

- **Веб-сборка лёгкая.** `dist/` — 18 файлов, 264 КБ кода; точка входа
  288 КБ (90 КБ gzip), стили 84 КБ (14 КБ gzip), 13 звуков ≈44 КБ. Бюджеты
  сторожит `test:build` (в том числе `mir.html` ≤ 30 МиБ; сейчас 27,4 МиБ).
- **Кэш и сжатие отдачи есть.** `server/serve.mjs`: `immutable` для
  `/assets/*` (имена хешированы), `no-cache` для оболочки, `ETag`, gzip по
  `Accept-Encoding`, `nosniff`; у Cloudflare — `public/_headers` с тем же
  правилом для `/assets/*`.
- **Секретов в исходниках нет.** Ключ панели — заводской публичный плюс
  секрет `MIR_ADMIN_KEY`; в `wrangler.toml` явно запрещено писать реальный
  ключ в `[vars]`.
- **Тело запроса нигде не буферизуется без границы.** И входной Worker, и
  Durable Object читают поток порциями до `MAX_REQUEST_BYTES` (512 КиБ) и
  отвечают 413, не пересылая лишнее.
- **Наблюдаемость включена.** `observability` с логами и трассами,
  `redact_query_string` (токен мог ходить в query), логи ошибок структурные,
  без query и заголовков.
- **Durable Object устроен по правилам.** SQLite-класс через миграцию `v1`,
  загрузка под `blockConcurrencyWhile`, запись только изменившихся ключей
  порциями по 100 (предел хранилища — 128), таймер уборки живёт, только пока
  открыт сокет.
- **Доступность в разметке выдержана.** Прогон по 130 `<button>` в `main.js`,
  `src/ui/` и виде карты: у каждой иконочной кнопки есть `aria-label`/`title`,
  кнопок без доступного имени и без текста нет.
- **Линтер: 65 замечаний, дефектов нет.** 27 — неиспользуемые имена (часть
  уже убрана в PR #53, остальное — `src/planet/`), 28 — `require-atomic-updates`
  (стилистика), 5 — `no-undef` у подстановок сборки и глобали service worker,
  3 — лишние экранирования, 1 — намеренное сравнение с собой в проверке
  детерминизма.

## Приоритет 1 — то, что видит игрок и что стоит денег

### 1.1. Установка офлайн-кэша качает 22,4 МБ (в PR #50)

**Что не так.** `PRECACHE` в собранном `sw.js` — 388 файлов, 22,4 МБ. Из них
363 файла и 22,0 МБ — редактор Azgaar в `/fmg/`; оболочка — 25 файлов, 440 КБ.
Первое открытие на телефоне по мобильной сети скачивает редактор, даже если
игрок ни разу не откроет карту.

**Как делать.** Разделить список надвое: оболочка ставится сразу, редактор
догружается отдельным **возобновляемым** проходом по просьбе страницы (после
старта и при возвращении во вкладку) и никогда — на «экономной» сети
(`saveData`, 2G). Бюджет установки (предлагаю 1,5 МБ) и обе половины списка
сторожить в `test:build`. Это уже написано в PR #50 — здесь важно не делать
второй раз и не мешать сведению.

**Проверка.** Первый запуск по медленному профилю качает ≤ 1,5 МБ; после
прогрева офлайн открывается карта; `test:build` падает, если оболочка выросла
или редактор вернулся в стартовый список.

### 1.2. Перебор пароля сдерживается только по IP (в PR #50)

**Что не так.** `DEFAULT_LIMITS` в `server/hub-core.mjs`: `/api/login` — 20
запросов в минуту на IP, `/api/register` — 10, окно минутное, ключ корзины
«ip + путь». За общим адресом (школа, офис, мобильный оператор) лимит делят
все, а перебор с сотни адресов по одному аккаунту не ограничен ничем — в
данных хаба нет счётчика неудачных попыток.

**Как делать.** Счётчик промахов **на аккаунт**: 6 неудач за 10 минут —
вход закрыт до окна; удачный вход счётчик снимает; в журнал панели попадает
только момент закрытия и имя, без пароля и токена. Правило живёт в
`hub-core.mjs` и зеркально в локальном бэкенде `store.js` (иначе офлайн-режим
и хаб разойдутся). Тоже уже написано в PR #50.

**Проверка.** `test:hub`: серия промахов закрывает вход, удачный вход снимает
счётчик, чужой IP не страдает; `test:worker`: то же через адаптер; локальный
режим — через `test:ui`.

### 1.3. Тумблер «Анимации» должен гасить движение везде (частично сделано)

**Что было.** Настройка «Анимации» ставит класс `reduce-motion` на `<html>`,
и CSS по нему гасит переходы. Но всё, что код двигает своим решением, класса
не видело: сначала это нашлось у вида карты блоками (появление и течение рек
бежали при выключенной настройке), теперь — у накладки генерации: она живёт в
документе Azgaar (iframe), куда CSS родителя не достаёт, и спрашивала только
системное `prefers-reduced-motion`.

**Сделано здесь.** Правило движения вынесено в одно место —
`src/ui/motion.js` (`motionQuery()` / `motionOff()`): системная настройка **или**
класс `reduce-motion`. Вид карты блоками и накладка генерации спрашивают его
заново на каждом шаге и кадре, поэтому переключение настройки действует на
открытом экране. Новая проверка `npm run test:stage` (25 проверок, jsdom)
сторожит и ход шагов конвейера, и «тихий режим» накладки.

**Что осталось.** В `src/style.css` девять блоков `@media
(prefers-reduced-motion: reduce)` — это слой системной настройки, он и должен
остаться медиазапросом (класс гасит анимации отдельно). Договорённость на
будущее: **новое движущееся место обязано звать `motionOff()`**; проверка —
`grep -rn "prefers-reduced-motion" src/` не должен находить ничего, кроме
CSS и `src/ui/motion.js`.

### 1.4. Настоящей проверки в браузере нет (не сделано)

**Что не так.** Все 16 наборов идут в Node, семь из них — в jsdom. jsdom не считает
ни пиксели, ни CSS-анимации, ни генерацию Azgaar целиком: «карта блоками»
рисуется в canvas 2D, и проверка честно пишет «без 2D-канваса вид не красит
кадр». В журнале есть упоминание прогона в headless Chromium (37 из 37), но
скрипта в репозитории нет — то есть проверка была разовой и не повторяется.

**Как делать (скилл `webapp-testing`).** Новый `scripts/test-browser.mjs`,
опциональная зависимость (как jsdom): без браузера набор печатает «пропущено»
и говорит `npx playwright install chromium`. Сценарий — по шагам скилла:
поднять сервер (`npm run serve` на 8787 или `with_server.py`), дождаться
`networkidle`, дальше **сначала разведка, потом действия**: снять скриншот и
консоль, найти селекторы, и только потом проверять. Что проверять первым
делом — то, что jsdom не может:

1. карта блоками: canvas не пустой (разнообразие цветов в `getImageData`),
   ползунок яруса меняет картинку, наложения включаются;
2. накладка генерации: подписи шагов идут, накладка исчезает, карта появляется;
3. лобби: два окна видят один кадр (по `mir.html` и по `dist/`);
4. консоль без ошибок на всех экранах.

**Проверка.** На машине с браузером `npm run test:browser` зелёный; в
песочнице без браузера — честное «пропущено». В CI ставить не сразу: сначала
посмотреть, как набор ведёт себя локально.

## Приоритет 2 — структура (из «что дальше» PR #50)

Порядок внутри приоритета важен: пункты 2.1 и 2.2 упрощают всё остальное.

**2.1. Обработчики по экранам.** В `main.js` словарь действий — 731 строка и
95 обработчиков на весь интерфейс. Пока словарь один, окна и лобби нельзя
вынести чисто: каждое вынесенное окно тянет за собой весь словарь. Делать
по шагам, по одному экрану за правку, начиная с самого обособленного
(«Настройки»), с прогоном `test:ui` и `test:perf` после каждого шага.

**2.2. Судьба `src/planet/`.** 9,6 тыс. строк, из интерфейса убрано, живёт в
мастерской (`/planet.html`) и в четырёх наборах проверок. Решение владельца:
`experiments/` (в бандл не попадает, но живёт) или удаление вместе с
набором `test:planet*`. Скилл `frontend-design` здесь не помощник: это вопрос
владения кодом, а не качества.

**2.3. `store.js` (1,7 тыс. строк) и `style.css` (5,8 тыс. строк).** Оба —
«одна дверь» для своего мира: состояние игры и оформление. Разделение по
доменам (аккаунты, друзья, панель, настройки) и по слоям CSS — работы на
несколько правок, каждая проверяется существующими наборами; порядок
каскада в CSS трогать нельзя (правила `test:spacing` читают файл как текст).

## Приоритет 3 — мелочи с ценой и риском

**3.1. `compatibility_date` в `wrangler.toml` — 2026-09-01.** Скилл
`workers-best-practices` советует держать дату свежей. Поднимать её нужно
осознанно: сверить изменения флагов между датами, затем прогнать
`test:worker`, `wrangler dev` и `test:hub` по живому `workers.dev`. Отдельная
правка, не «заодно».

**3.2. Отложенная запись присутствия — не `setTimeout`.** В `MirHub.persist()`
запись «был в сети» откладывается таймером, если окно `PRESENCE_WRITE_MS`
закрыто. Если объект вытеснят в этом окне, отметка теряется (для присутствия
не страшно, для данных — уже нет): скилл `durable-objects` предлагает
`state.storage.setAlarm()`, который переживает вытеснение. Решать по цене:
сейчас изменение косметическое, но привычка «важное — через alarm» дешевле,
чем разбираться с потерянной записью потом.

**3.3. Код-приглашение проверяется в четырёх местах.** Регулярка
`^[A-Z0-9]{4}-[A-Z0-9]{4}$` и текст ошибки живут в `src/data/store.js` (два
раза), `server/hub-core.mjs` и `server/hub-lobby.mjs`. Одна функция в
`hub-core.mjs` + зеркало в `store.js`, как требует договорённость «правило —
в одном месте». Без спешки: пока копии совпадают, вреда нет, но следующая
правка формата кода разойдётся молча.

**3.4. `server/data/mir-hub.json` — 1,8 КБ с солью, хешем пароля и токеном
устройства, лежит в репозитории.** Рабочий путь данных — корневой `data/`
(в `.gitignore`), файл из `server/data/` не читает никто: похоже, остаток
прежней раскладки. Убрать или переложить — решение владельца (это его данные,
пусть и тестового аккаунта).

## Порядок работ

1. **Свести PR #50** (или его критическую часть: офлайн-кэш и вход под замком).
   Он делает 1.1 и 1.2 и трогает `main.js`, `style.css`, `sw.js`, `index.html` —
   начинать структурные работы раньше значит конфликтовать с ним.
2. **PR #53** (чистка и правило движения) — независим, можно сводить раньше.
3. **Проверка в браузере (1.4)** — после сведения: она и есть страховка для
   следующих шагов, где jsdom молчит.
4. **Структура (2.1 → 2.2 → 2.3)** — по одной правке, с проверками после каждой.
5. **Мелочи (3.1…3.4)** — между делом, каждая отдельной записью в журнале.

## Чего не делать

- **Не менять визуальный язык.** Скилл `frontend-design` предупреждает про
  «шаблонные» приёмы (капс с разрядкой, одиночное слово в акценте, карточки с
  одним радиусом) — но правила проекта заданы владельцем и выдержаны:
  тёмная тема, острые углы, волосяные линии, капс в подписях. Бриф сильнее
  общего совета: переписывать оформление «как в скилле» не нужно.
- **Не оптимизировать то, что уже дешёвое.** 90 КБ gzip кода на старте — не
  предмет работы; загрузку тормозит установка кэша (1.1), а не бандл.
- **Не «чинить» замечания линтера, которые не являются дефектами** (см.
  «Что уже в порядке») и не включать правила, переписывающие стиль проекта.
- **Не трогать руками `public/fmg/` и `vendor/`**, не патчить `mir.html` и
  `dist/` регулярками: только `npm run fmg:build`, `npm run build`,
  `npm run single`.
- **Не гнаться за Core Web Vitals в этой песочнице**: без браузера это
  самообман. Сначала 1.4.
