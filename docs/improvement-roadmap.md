## P0 — база с чувствительными данными в Git

**Наблюдение.** `server/data/mir-hub.json` отслеживается Git (проверено через `git ls-files`). В текущем файле есть пользовательские записи с полями `salt`, `passHash` и `tokens`. `.gitignore` уже запрещает новые файлы `server/data/`, но это не исключает ранее добавленный файл и не удаляет его из истории.

**Сделано в рабочей ветке.** `server/data/mir-hub.json` удалён из Git-индекса, а локальная копия оставлена на диске и игнорируется (данные владельца не удалялись). Автоматическая ротация не выполнялась, так как неизвестно, являются ли записи тестовыми и используются ли где-либо эти сессии. Если записи могли быть рабочими, нужно отозвать токены и сбросить пароли затронутых аккаунтов.

**Осталось.** Файл остаётся в истории Git; проверка истории и её переписывание — отдельное согласованное действие. История не переписывалась автоматически.

**Проверка.** `git ls-files server/data/` теперь пуст; локальный файл сохранён. Проверить `git log --all -- server/data/mir-hub.json` перед решением по истории.

## P1 — тесты до публикации и настоящая браузерная проверка

**Наблюдение.** `.github/workflows/deploy.yml` выполняет `npm ci`, `npm run build`, затем deploy. Тестовые скрипты в package.json есть, но workflow их не запускает. Текущая среда также не имеет установленных `vite`/`jsdom`, поэтому нельзя считать проходящими те тесты, которые здесь не удалось запустить.

**Сделано в рабочей ветке.** Workflow теперь запускается на pull request в `main`; job `verify` выполняет сборку, unit/integration-тесты и Playwright smoke-сценарий, а job `deploy` зависит от успеха `verify`. Добавлены проверки главного экрана, окна настроек, отсутствия ошибок консоли и offline reload через service worker.

**Ограничение проверки здесь.** Все Node/jsdom тесты и сборка проходят локально. Бинарник Chromium через Playwright CDN скачать в этой среде не удалось (сетевое соединение сброшено), поэтому сам браузерный сценарий остаётся непроверенным локально и должен впервые пройти в CI. Скриншот при падении пока не сохраняется.

**Следующий шаг.** Убедиться по первому запуску CI, что Chromium smoke стабилен; затем добавить автоматический скриншот при ошибке, если он помогает разбору.

## P2 — разрезать главный UI-модуль небольшими шагами

**Наблюдение.** `src/main.js` около 5,1 тыс. строк и содержит большой словарь обработчиков действий (примерно от строки 4168). Он одновременно связывает несколько экранов, состояние окон и эффекты.

**Сделано в рабочей ветке.** Разметка экрана настроек вынесена в `src/ui/settings.js`; зависимости передаются явно, а `src/main.js` отвечает за передачу текущего состояния. Добавлен небольшой тест модуля и сохранён UI smoke-тест.

**Следующий шаг.** Проверить браузерный прогон и продолжать только аналогичными небольшими шагами; остальные обработчики не перемещались.

## P2 — отложенная запись Durable Object

**Наблюдение.** В `server/hub-core.mjs` таймеры на строках около 1460 обслуживают ожидание inbox — это не сохранение присутствия. В старом плане упоминалась потеря отложенной записи presence, но её нельзя подтвердить по одному этому совпадению: перед изменением нужно проследить фактический путь записи presence в `MirHub` и вызов `persist()`.

**Сделано в рабочей ветке.** Найден trailing `setTimeout` для presence в `hosting/cloudflare/worker.js`; он заменён на `storage.setAlarm()` и метод `alarm()`, который сохраняет diff через существующий `flush()`. Таймеры длинного опроса inbox не менялись. Тест `test:worker` назначает alarm и проверяет сохранение без следующего HTTP-запроса.

**Проверка.** `npm run test:worker` проходит. Нужно также подтвердить поведение в `wrangler dev`/Cloudflare runtime до production deploy.

## P3 — формат приглашений: закрепить уже начатую централизацию

**Наблюдение.** В этой рабочей ветке введён `src/data/invite-code.js`; клиент, ядро хаба и партии используют `isInviteCode`. Это устраняет дублирование проверки формата в обработчиках и валидации импортируемых данных.

**Сделано в рабочей ветке.** Добавлен `src/data/invite-code.js`, и проверка подключена в клиенте, ядре хаба и обработчике партии. `scripts/test-invite-code.mjs` проверяет регистр, длину, разделитель, пробелы и типы; нормализация ввода осталась отдельно.

**Проверка.** `npm run test:invite-code`, `npm run test:parties` и живой `npm run test:hub` прошли; старые копии regex в трёх перечисленных файлах отсутствуют.

## Что не стоит делать первым

- Не обновлять `compatibility_date` Cloudflare «просто на свежую дату»: сначала сверить breaking changes и прогнать worker/hub тесты.
- Не менять формат/поведение service worker и offline cache без браузерного теста: там уже есть разделение приложения и `/fmg/`, навигационный fallback и обновление без принудительной перезагрузки.
- Не делать массовый рефакторинг `src/style.css` или `src/planet/` без конкретной цели и теста; большие объёмы сами по себе не доказывают дефект.
- Не полагаться на старые численные выводы из `docs/improvement-plan.md`: документ содержит датированный анализ 2026-10-13 и часть пунктов могла измениться. Этот файл — свежий список наблюдений, а не замена тестов и аудита перед каждой задачей.
